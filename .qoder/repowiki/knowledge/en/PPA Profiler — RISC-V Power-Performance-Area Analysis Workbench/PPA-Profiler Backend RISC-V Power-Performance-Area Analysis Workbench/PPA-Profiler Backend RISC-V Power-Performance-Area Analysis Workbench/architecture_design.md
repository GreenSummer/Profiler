The module is organized as a layered FastAPI application (`main.py`) whose routes delegate to a pure query/analysis layer (`analysis.py`) — one function per view (V1–V11) — so the LLM agent calls only these typed functions, never raw SQL. Data persistence uses SQLModel models (`models.py`) over a single SQLite file configured via `config.py` (`ppa.db`). Ingestion (`ingest.py`) reads tool output files listed in `manifest.json`, dispatches each report kind through pluggable parsers under `parsers/` (`rtla.py`, `primepower.py`, `specint.py`) that return dataclasses defined in `parsers/base.py`, canonicalizes module paths via `canonicalize.py`, persists tall metric rows (`AreaRow`, `PowerRow`, `TimingPath`, `PerfRow`, `Metric`), and finally invokes the rule engine. The rule engine (`rules.py`) loads YAML rules from `rules_pack.yaml`, materializes a `RunFacts` snapshot per run, and evaluates a fixed registry of evaluators (`EVALUATORS`) producing `Finding` rows. The AI subsystem lives in `ai/` with a strict trust contract: `agent.py` drives a tool-calling loop over `tools.py` against an OpenAI-compatible LLM (`llm.py`, e.g. Ollama/vLLM) and falls back to a deterministic offline analyst when the endpoint is unavailable; chat sessions are persisted as `ChatSession`/`ChatMessage`. A Typer CLI (`cli.py`) provides `init`, `gen-sample`, `ingest`, `demo`, `serve`, and `check-format` commands, while `metrics.py` holds shared aggregation helpers (summaries, figures-of-merit, Pareto front). Dependency direction is strictly: routes → analysis → metrics/models/db; ingestion → parsers/canonicalize → models/rules; AI → tools → analysis (no reverse edges).
